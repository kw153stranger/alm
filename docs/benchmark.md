# 방법론 기반 산출물 자동생성·관리 + Gate 승인 서비스 — 기능 벤치마킹 (심화)

> 요구사항 재정의: A안(구조화된 방법론 자산관리)을 기반으로 하되,
> ① 실제 개발툴(IDE·Git·CI/CD·이슈트래커)과 연계하여 산출물이 **자연스럽게(자동으로) 생성**되고,
> ② 그 산출물이 **중앙에서 통합관리**되며,
> ③ 단계별로 **Gate 승인**(전자서명/리뷰워크플로우)이 진행되는 서비스
> 조사 시점: 2026년 7월

이 요구사항은 RMC/EPF의 후속·현재진행형 버전이라 할 수 있는 **IBM ELM(Jazz 플랫폼)**, **Siemens Polarion ALM**, **PTC Codebeamer** 3사가 정확히 다루고 있는 영역입니다. 셋 다 규제산업(항공/자동차/의료기기/금융)에서 "방법론 준수 + 산출물 추적성 + Gate 승인"을 핵심 가치로 판매하는 살아있는(현재도 업데이트되는) 제품입니다.

---

## 1. IBM Engineering Lifecycle Management (ELM) — RMC의 실질적 후속

RMC/EPF가 "프로세스를 문서로 정의·발행"하는 데 그쳤다면, ELM(Jazz Team Server 기반)은 그 방법론을 **실행 가능한 워크플로우와 도구 연동으로 구현**합니다.

### 구성 제품군
| 제품 | 역할 |
|---|---|
| DOORS / DOORS Next | 요구사항 수집·추적·변경관리(입력 산출물의 원천) |
| EWM (Engineering Workflow Management) | 작업항목(계획/태스크/결함/변경) 관리, **커밋·빌드·CI/CD 파이프라인 결과와 작업항목을 자동 연결** |
| ETM (Engineering Test Management) | 테스트 계획/설계/실행/결함(출력 산출물) |
| Rhapsody Model Manager | 모델 기반 설계 산출물 형상관리 |
| Engineering Insights / Jazz Reporting Service | 전체 산출물 간 관계 시각화, 대시보드 리포팅 |

### 핵심 매커니즘 (사용자 요구사항과 직접 매칭)
- **자동 산출물 생성**: 문서 생성 솔루션이 ELM 제품 및 XML/REST를 사용하는 타 벤더 데이터를 자동으로 취합해 PDF/HTML/Word/Excel 문서로 산출 — "산출물을 따로 작성"이 아니라 "작업 데이터에서 자동 도출"
- **개발툴 연계**: EWM이 작업항목을 소스코드 커밋, 빌드 결과, CI/CD 파이프라인 산출물과 연결해 "어떤 변경이 어떤 작업항목에 의한 것이고 어느 빌드에 반영됐는지" 자동 추적
- **Gate 승인**: 전자서명(Electronic Signature)과 역할기반 권한으로 산출물 리뷰·승인 워크플로우 진행. 커스터마이즈 가능한 워크플로우로 "올바른 사람이, 올바른 시점에" 작업항목을 편집·승인하도록 강제
- **디지털 스레드(Digital Thread)**: OSLC(Open Services for Lifecycle Collaboration)라는 개방형 표준으로 요구사항–설계–개발–테스트 전체를 연결 → 표준화된 개방형 연동이라 자체 서비스 설계 시 참고할 만한 아키텍처 패턴
- **베이스라인/스냅샷**: 프로젝트의 특정 시점 상태를 통째로 캡처해 과거 시점과 비교 가능 (감사 대응)
- **써드파티 연동**: Jira, PTC Windchill 등과 연동 애드온 제공

### 시사점
가장 "정석적인" 참고모델입니다. 다만 IBM Jazz 플랫폼 자체가 무겁고 구축·운영 난이도가 높아, **자체 서비스 기획 시에는 이 아키텍처의 개념(작업항목↔커밋↔빌드 연결, OSLC식 개방형 링크, 전자서명 Gate)을 경량화해 벤치마킹**하는 방식이 현실적입니다.

## 2. Siemens Polarion ALM

### 핵심 기능
- **LiveDocs**: 요구사항 명세서를 문서 형태(워드 유사 UI)로 작성하면서도 문단 단위로 개별 추적 가능한 작업항목으로 관리 — "문서 작성"과 "산출물 데이터베이스화"를 동시에 해결
- **전자서명 승인 워크플로우**: 이해관계자가 명세 문서를 전자서명으로 검토·승인해야 운영(release) 단계로 진행 가능 — **요청하신 Gate 승인과 정확히 일치하는 기능**
- **Git/SVN 네이티브 연동**: 모든 산출물(요구사항, 검증절차, 프로젝트 계획/태스크)이 버전관리 저장소에 저장되어 모든 변경에 대해 자동으로 이력(버전) 기록 생성
- **변경관리(Change Request)**: 변경요청 접수→검토→구현→소스코드 수정 이력까지 완전한 추적성 보장
- **글로벌 설정 버전관리**: 프로젝트 구성 자체도 버전관리되어 프로세스 개선 이력까지 추적 가능

### 시사점
Git 연동이 매우 강력하고(사용자가 원하는 "개발툴과 자연스럽게 연계"에 가장 근접), "문서 작성 경험"과 "구조화된 데이터"를 동시에 잡는 LiveDocs 컨셉은 실무자 채택 저항을 줄이는 데 유용한 설계 아이디어입니다.

## 3. PTC Codebeamer

### 핵심 기능
- **컴플라이언스 템플릿**: ISO 26262, IEC 62304, DO-178C, FDA 21 CFR Part 11 등 표준별 사전 구성 템플릿 즉시 사용 가능
- **고도로 설정 가능한 워크플로우**: 애자일/워터폴/하이브리드 방법론別 브랜칭, 병합, 승인, 역할기반 접근제어를 모두 지원 — **자체 방법론을 코드/설정으로 이식하기 좋은 유연성**
- **DevOps 연동**: Jenkins, AWS, Jira와 연동해 CI/CD 파이프라인과 ALM 프로세스를 직접 연결, 빌드·배포 추적성 확보
- **Working Sets & Branching**: 변형(variant)·병렬개발 관리에 특화 — 여러 프로젝트/제품 라인에서 공통 방법론을 유지하면서 부분 커스터마이징 가능

### 시사점
"방법론을 프로젝트별로 유연하게 재구성하면서도 표준은 유지"하는 목적에 가장 근접한 유연성을 제공합니다. 다만 리뷰에 따르면 UI가 다소 올드하다는 평가도 있어(참고: PeerSpot 사용자 리뷰), UX 설계 시 유의할 지점입니다.

| 비교축 | IBM ELM | Polarion (Siemens) | Codebeamer (PTC) |
|---|---|---|---|
| 태생 | RMC/RUP 계보 → Jazz 플랫폼 | 독자 개발 → Siemens 인수 | 독자 개발 → PTC 인수 |
| 산출물 생성 방식 | 여러 도구 데이터 취합 후 자동 문서 생성 | LiveDocs(문서+DB 동시) | 브랜칭 기반 템플릿 재사용 |
| Gate 승인 | 전자서명 + 역할기반 워크플로우 | 전자서명 승인 워크플로우 | 역할기반 승인 + 커스텀 워크플로우 |
| 개발툴 연계 | EWM이 커밋·빌드·파이프라인과 작업항목 연결(OSLC 개방표준) | Git/SVN 네이티브, 커밋↔작업항목 추적성 지표 제공 | Jenkins/AWS/Jira 연동 |
| 컴플라이언스 템플릿 | 강함(SAFe, DO-178, ISO26262 등 대응 사례多) | 우수(ISO/FDA 등, 일부 유료 커스터마이징) | 매우 강함(즉시 사용 가능한 템플릿 다수) |
| 학습곡선/구축난이도 | 높음(엔터프라이즈급, 무거움) | 높음(Siemens 인프라 의존적) | 중간~높음(기능 과다로 복잡하다는 평도 있음) |
| UI/UX 평가(사용자 리뷰 기준) | 보통 | 문서형 UI로 친숙 | 다소 올드하다는 평 존재 |

## 5. 서비스 설계에 반영할 아키텍처 패턴 제안

위 3사의 공통 패턴을 자체 서비스 설계에 다음과 같이 반영할 수 있습니다.

1. **작업항목(Work Item) 중심 데이터 모델**: 요구사항·태스크·산출물·테스트를 모두 "작업항목"이라는 공통 객체로 표현하고, 서로 링크(추적성)를 갖게 설계
2. **Git/이슈트래커 훅 기반 자동 산출물 생성**: 커밋 메시지·PR·이슈 상태 변경 이벤트를 트리거로 삼아, 방법론에서 정의한 산출물 템플릿에 자동으로 데이터를 채워 넣는 방식(EWM의 커밋↔작업항목 연결, ELM의 자동 문서 생성 방식 응용)
3. **Gate = 상태 전이(State Transition) + 승인자 서명**: 방법론의 각 단계를 워크플로우 상태값으로 정의하고, 상태 전이 시 지정된 승인자의 전자서명(또는 승인 클릭)이 있어야 다음 단계로 진행되도록 설계(Polarion 전자서명 방식)
4. **문서형 뷰 + 구조화된 DB 이중화**: 실무자에게는 익숙한 문서(Word/Markdown) 형태로 보여주되, 내부적으로는 문단/항목 단위로 구조화된 데이터로 저장(Polarion LiveDocs 방식) → 최근 트렌드인 Docs-as-Code(Backstage TechDocs)와도 연결 가능
5. **개방형 연동 표준 고려**: 향후 확장성을 위해 OSLC류의 개방형 링크 표준 또는 최소한 REST API 기반의 표준화된 아티팩트 스키마를 설계 초기에 정의
6. **베이스라인/스냅샷**: 감사 대응을 위해 특정 시점의 전체 산출물 상태를 스냅샷으로 저장하는 기능
